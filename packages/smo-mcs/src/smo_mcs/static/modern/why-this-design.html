Why this console looks the way it does

EOSAT-1's console is a teaching artefact. A student who spends forty hours in it will absorb its habits — so every choice here models the practice of real mission control rooms, and this page says why. The full rationale lives in docs/design_2026-08/PRINCIPLES.md.

Grey is the resting state

A fully nominal spacecraft produces a screen with essentially no colour on it. This is the ISA-101 / high-performance-HMI rule: colour is the strongest pre-attentive signal we have, so it is spent only on deviation — amber for a yellow-limit violation, red-orange for a red one, hatched grey for stale data, blue only for interaction and the commanded state. Industrial studies report roughly a 48 % improvement in detecting abnormal situations before alarms occur on greyscale-baseline displays. If this page looks subdued, that is the point: the day it lights up, something is wrong.

Try the GREY toggle in the header. The console must stay fully operable in greyscale — every status carries a glyph, a border or a text label alongside its colour, because ~8 % of male students cannot reliably separate red from green.

The four-question header

The situational-awareness header answers, permanently and in order, the four questions a spacecraft operator must never have to hunt for:

SEECan I see it? — telemetry link freshness, active vs commanded TM tier (a demoted link says so), on-board store fill.
TALKCan I talk to it? — the carrier→bit→frame lock chain, the last telecommand verdict, which ground station we are in contact with.
WELLIs it well? — spacecraft mode as telemetered (the sub-label tells you the source), alarm counts, load-shed level.
NEXTWhat's next? — AOS/LOS countdown, next eclipse, next scheduled activity. Real flight controllers are graded on anticipation.

The schematic is the navigation

You reach the EPS page by clicking the battery on the overview schematic, not by decoding a tab acronym. This is the ISA-101 display hierarchy: L1 overview (one screen, whole spacecraft), L2 subsystem (the controller's home), L3 equipment, L4 diagnostics (the raw PUS service panels). The rail on the left is an accelerator for people who already know where they are going.

A number without its limits is not information

Every limit-checked parameter renders as a triad — numeral, unit, deviation bar with the yellow and red boundaries drawn as ticks. Ground limit checking is the core MCS concept this simulator teaches; on the old console the limits were invisible, so a student saw a number turn yellow and could not learn what yellow meant. Parameters without limits say no limit defined out loud rather than looking identical.

Stale must never look like steady

After loss of signal, charts stop appending and values become a hatched em-dash. A flat line of repeated last-values is a lie the display tells confidently — distinguishing "the spacecraft is fine" from "I cannot see the spacecraft" is a core LEOP lesson, so a post-LOS screen is supposed to look loudly empty.

Alarms are a managed system, not a log

The alarm drawer follows ISA-18.2: four priorities assigned by consequence and required response time (not raw event severity), per-alarm rationalisation (cause · consequence · response) where the config provides it, one single alarm authority that every other indicator merely counts, a one-click link from any alarm to its procedure, and blink reserved exclusively for unacknowledged P1. The ⛓ button on every row opens the causal chain: command → acceptance → execution → parameter moves → limit crossed → alarm → procedure, assembled on one screen — because that chain is the mental model this simulator exists to install.

What is honestly simulation

This is a training system, and it says so rather than pretending. The TRAINING chip appears only when the ground clock is simulator time; the FDIR page's autonomy panel is titled SIMULATED ON-BOARD AUTONOMY (instructor truth — not downlinked) and vanishes in real-mission mode, because no real spacecraft downlinks its own fault-cascade queue. Spacecraft mode is read from telemetry parameter 0x0700 and every rendering carries a provenance sub-label. When a value only exists inside the simulator, the console either labels it as such or refuses to show it.

GUIDED mode

The GUIDED toggle overlays numbered teaching annotations (from configs/eosat1/mcs/annotations.yaml) and expands every deviation bar's tick labels. It is off by default: the annotations are scaffolding, and scaffolding comes down.
